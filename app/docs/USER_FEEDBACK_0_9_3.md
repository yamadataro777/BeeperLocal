# 0.9.3：利用者フィードバックの修正

2026-10-03。画像送信、会話相手のアイコン再読み込み、Instagram認証失敗の説明、macOSキーチェーン確認の繰り返しに加え、LINE失効時の接続表示とInstagramの本人確認経路を改善した内部検証候補。

## 今回の変更

| 指摘 | 修正 |
| --- | --- |
| 画像が送れない | LINE・Instagram・Slack・X・Messengerの画像送信経路と共通の画像選択画面を追加。ファイル選択、貼り付け、ドロップ後にプレビューし、本人が送信ボタンを押す。 |
| 閉じて開くと相手アイコンが再表示される | LINE・InstagramのアイコンとSlackプロフィールを暗号化DBへ保存。再起動・オフライン時にも保存分を表示し、画面切り替えによる再取得を抑止。 |
| Instagram認証の失敗理由が不明 | ユーザー名・パスワードの拒否、確認コードの拒否、追加認証・アカウント対応、原因を特定できないログイン拒否、タイムアウトを固定の日本語説明に分離。 |
| LINEを本家Beeper等に連携し直すと切れたまま接続表示が残る | ログイン失効をCLI→Core→画面へ通知。受信・履歴同期を止め、再ログイン表示と手動再連携ボタンへ切り替え。保存履歴・下書きを保持。 |
| Instagramの認証通知が届かない | 公式サイトの専用ログインウィンドウを追加。本人確認を同じログイン画面で進め、公式画面に提示される別の方法を選べるようにした。 |
| 毎回キーチェーン確認が出る | GUIプロセス内のメモリで読み取りを共用し、同一内容の書き戻しを省略。キャンセル後は本人が再接続するまで同じアクセスを繰り返さない。Macとサービスのパスワードの違いを画面へ追記。 |

画像は1枚ずつ、JPEG・PNG、4MiB・2,500万画素以内。画像だけを送り、入力中の文章は下書きに残す。回転情報を適用したうえでEXIF/GPS等を除き、送信用画像や資格情報の平文一時ファイルは作らない。送信済み画像の表示用縮小画像は暗号化して保存する。

送信前に宛先とアカウントを検証し、画像のハッシュと送信要求IDを暗号化台帳に記録する。同じ要求IDを再送しない。結果が不明な場合は履歴・相手側で確認した旨を本人がチェックするまで、画面からの再送を止める。サービスへの書き込み要求を自動で繰り返さない。

## サービスごとの範囲

| サービス | 画像送信の経路・条件 |
| --- | --- |
| LINE | 既存の1対1会話。画像用の暗号化メディアと画像メッセージを使用。 |
| Instagram | 取得済みDM・参加済みグループ。画像アップロード後、同じ検証済み会話へ送信。 |
| Slack | 連携済み会話。公式の外部ファイルアップロード・完了APIを使用。追加の `files:read` / `files:write` 権限が必要。既存の許可内容は自動で変わらない。 |
| X | 取得済みChat会話。署名を検証した会話鍵で画像を暗号化し、暗号化メディアをアップロード。実際のXDKで生成したメッセージと応答の署名・画像情報を検証。 |
| Messenger | 既存端末セッションの1対1会話。暗号化アップロードと画像メッセージを使用。受信画像の取得・表示と過去の暗号化バックアップ復元は今回の対象外。 |

アイコンは各アカウント最大128件の保存キャッシュ。LINEは画像パス、Instagramは画像URLのパス変更時に更新する。InstagramのCDN署名パラメータだけの変更では再取得しない。Slackは保存分を表示しつつ期限に応じて更新する。対象サービスのローカルデータ削除時には画像キャッシュも削除する。

## LINEの同時利用とInstagramの本人確認

本家BeeperのLINE bridgeと本アプリのLINE CLIは、Chrome ExtensionとしてLINEへ接続する方式を使う。この枠は単一セッションで、別の同方式クライアントへのログインにより既存セッションが失効し得る。[Beeper公式実装の説明](https://github.com/beeper/line)を参照。サーバー側の制限を変更する修正ではない。Chrome版・本家Beeper・BeeperLocalを同じアカウントで並行利用する方法は提供せず、勝手な再ログインで接続を取り合うこともしない。スマートフォンのLINE利用と、すべてのMac／PC公式アプリとの競合を同一視しない。報告端末の正確なアプリ種別は未確認。

LINE CLIは受信ストリームから応答が来るまで準備完了とせず、内部の再接続も画面へ通知する。無通信中にも約30秒間隔の認証確認を行うが、通信待ち・スリープ中の即時検知は保証しない。強制ログアウトの固定コードを受けたら、関連する受信・履歴同期を止める。保存履歴と下書きは残し、本人が使うアプリを決めてから再連携する。

Instagramの専用ウィンドウは毎回新規の非永続WebKitセッションで、既存Safari／Chrome／BeeperのプロファイルやCookieを読み出さない。ログイン先はHTTPSのInstagramドメインに限定する。本人が画面内で認証して完了ボタンを押した後、その専用セッションだけを非公開パイプでアダプタへ渡し、Directの接続とアカウントを確認してからKeychainへ保存する。通知が発行されたと決めつけた案内を廃止し、公式画面に提示された別の確認方法を使うよう案内する。Instagram側が代替手段を提供しない場合やアカウントを制限する場合まで解消したとは扱わない。

## キーチェーンの説明

OSの確認画面にはMacのログインパスワードを入力する。本人が信頼する配布元を確認したうえでmacOSの「常に許可」を選ぶと、同じ署名のアプリへの継続的な許可を設定できる。「許可」は今回のアクセスのみ。

アプリからKeychainのACL・パスワード・DB暗号鍵を変更する処理は追加していない。OSの許可状態や別Mac固有の状態による確認まで、完全に出なくなるとは保証していない。キャンセル後の再接続は本人操作に限る。資格情報のメモリキャッシュはGUI終了時に破棄する。

## 検証と残る範囲

架空データのCore・画面・Go・Rustテストと署名済み配布物の検査結果は `desktop-0.9.3-verification.json`、ZIP照合は `desktop-0.9.3-package-verification.json` に記録する。

Core全515件が成功。画面は全75件中74件が成功し、追加したLINE試験の履歴テキスト比較を修正して、対象12件（設定・LINE）を再実行して成功。累計75ケースを確認した。署名済みCoreの実bytecode 41モジュールを用いた33件も成功（依存ライブラリとfixtureはビルド環境）。Rust 6件、LINE・Instagram・X・Messengerの関連Go試験、shell構文7ファイル、offline demo、production buildを確認。LINEの無通信状態での失効検出、受信準備完了／再接続の区別、履歴同期の遅延応答で接続済みに戻らないこと、送信抑止・下書きと保存履歴の保持を回帰試験で確認。Instagramは新規ウィンドウの非永続性、許可ドメイン、キャンセル・検証失敗時の保存抑止、本人確認後のアダプタ接続検証を確認した。画像送信時の宛先とボタンは640×500でも見える。スクリーンショットは架空データのみ。

署名済み候補は9実行ファイル＋Core内85 Mach-Oを検査し、同じDeveloper IDと通常0.8.5との相互署名要件を確認した。全94個がarm64・最低OS13.0以下で、開発用外部ライブラリへの依存はない。空HOME・OS標準PATH・開発用CAなしでCore、Instagram新規helper、Slack設定補助、公開TLS、5サービスのIPC起動を確認。Keychain項目を読み書きせず、DBは作成されていない。Apple公証は未実施。

**実アカウントでの画像送信は実施していない。** 各サービスの画像が実際に届くこと、相手側の表示、利用者のMacでのInstagram本人ログインとキーチェーン確認回数は未検証。モック応答や暗号ライブラリの試験を実サービスの成功と扱わない。

通常配置の0.8.5は置き換えない。Apple公証、Slack公開OAuth設定、別Macまたは別OSユーザーでの初回ログインという0.9.2からの一般配布条件も残る。`FRESH_MAC_AUDIT.md` は0.9.2監査時点の記録として保持する。

実装の参照資料：Slack公式の [アップロードURL取得](https://docs.slack.dev/reference/methods/files.getUploadURLExternal/) と [アップロード完了](https://docs.slack.dev/reference/methods/files.completeUploadExternal/)、X公式の [Chat media SDK資料](https://github.com/xdevplatform/docs/blob/main/xchat/media.mdx)。インストール済みXDKでは送信時の `media_type` に数値を渡す必要があり、実SDKの往復試験で確認した。
