==================================================
1. BeeperLocalの目的
==================================================

BeeperLocalの本質的な目的:

Beeperのような複数メッセージサービス統合を、
Beeper側のCloud Bridgeへ依存するのではなく、
ユーザー自身のMac上でLocal-firstに実現する。

単にメッセージ本文を何らかの方法で取得することが目的ではない。

目標アーキテクチャ:

Messaging Services
    ↓
Local Connectors
    ↓
UnifiedMessage
    ↓
Local encrypted storage
    ↓
Unified Inbox / Search / Send

理想:

Telegram ─┐
Matrix ───┤
Slack ────┼→ Local Connector Layer
LINE ─────┤
etc. ─────┘
               ↓
        UnifiedMessage
               ↓
         AES-256-GCM
               ↓
       Local SQLite DB
               ↓
      Search / Inbox / Send

重要な設計思想:

- Cloud Bridgeを極力使わない
- メッセージ本文はLocal処理
- credential/sessionはmacOS Keychain
- 保存本文は暗号化
- plaintext FTSを作らない
- provider固有実装とUnifiedMessage層を分離
- 技術的成立性と商用/規約成立性を別Gateとして扱う

13. line-cli Error Handling — 実コード確認済み
==================================================

以下はユーザーMac上のline-cli sourceから直接確認済み。


13.1 History path

internal/messaging/client.go:

History()
    ↓
Session.Do(...)
    ↓
api.GetRecentMessagesV2(chat, limit)

さらに:

pkg/line/methods.go:

GetRecentMessagesV2()
    ↓
callRPC(
  "TalkService",
  "getRecentMessagesV2",
  chatMid,
  limit
)

重要:

HistoryではまずRPC取得を行い、
その後にDecode/E2EE処理へ進む。

したがって現在のhistory failureは、
message decryptより前のRPC段階で発生している可能性がある。


13.2 Send path

Sendでは:

Letter Sealing preparation
    ↓
ReserveSequence
    ↓
Message construction
    ↓
Session.Mutate(...)
    ↓
api.SendMessage(seq, msg)
    ↓
TalkService/sendMessage

という経路。

E2EE準備に失敗した場合には、

could not prepare encrypted message...

など専用errorを返すコードが存在する。

今回実際に出たのはそれではなく、

LINE request failed...

なので、

少なくともE2EE preparationを通過し、
SendMessage RPC側まで進んだ後にfailureしている可能性が高い。


==================================================
14. RemoteError sanitization
==================================================

internal/session/manager.go に:

type RemoteError struct {
    Action string
    cause error
}

が存在。

RemoteError.Error() はraw causeをユーザーへ表示しない。

non-auth errorの場合:

LINE request failed; check your connection and LINE account settings

へ変換する。

つまり現在Terminalで見えているerrorは、
LINE Serverから返された本当のerrorそのものではない。

また:

ProtocolError(err)

が存在し、
RemoteError内部のcauseをunwrapできる。

ただしclassification用であり、
raw protocol responseをそのまま表示してはいけない。

15. Authentication / Token Refreshについて
==================================================

重要な訂正事項。

過去のDeep Researchの一部回答で:

「line-cliにはtoken refreshがない」
「IsRefreshRequiredがない」
「EncryptedKeyChain/E2EEPublicKeyがない」

等の記述があった。

これは誤り。

ユーザーの実コードから以下が確認済み:

RefreshAccessToken
RefreshAccessTokenContext
Manager.do
IsRefreshRequired
IsAuthError
EncryptedKeyChain
E2EEPublicKey

が存在する。

Manager.doでは:

- RefreshDeadlineによるscheduled refresh
- auth error検出
- refresh tokenによるrefresh
- read-only callのretry
- mutationをreplayしない処理

が存在。

IsRefreshRequiredは少なくとも:

- code 119
- "access token refresh required"
- MUST_REFRESH_V3_TOKEN
- TokenAuthException code 4

を認識する。

したがって、

「code 119がrefreshされずgeneric errorになっている」

を現時点の最有力原因として断定してはいけない。

今回の実際の出力がgeneric non-auth RemoteErrorなので、
最終causeはline.IsAuthError分類ではない可能性が高い。


==================================================
16. Manager.do の重要仕様
==================================================

Read-only:

Manager.Do
    ↓
Manager.do(... retry=true)

Auth errorの場合、
credential refresh後に1回retry可能。

Mutation:

Manager.Mutate
    ↓
Manager.do(... retry=false)

mutationはreplayしない。

コードコメント:

A lost response may mean the server already accepted the mutation.

これはBeeperLocalでも維持すべき重要な設計原則。

送信系mutationのblind retryは禁止。

17. callRPC実装
==================================================

callRPCWithBaseURLContext は:

LINE Chrome gateway

へHTTP POST。

設定される主要header:

Content-Type: application/json
User-Agent
x-line-chrome-version
x-line-application
x-lal
x-line-access
Cookie: lct=...
x-hmac

HMAC signatureも生成。

その後:

HTTPClient.Do(req)

response body取得

responseError(status, body)

を実行。

status != 200
または
IsAuthError(err)

の場合はerror return。

HTTP 200のnon-auth envelopeについては
method-specific handlingへ渡す設計。
